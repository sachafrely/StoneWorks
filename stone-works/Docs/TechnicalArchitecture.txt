# 1. High-level architecture

Starting Major Systems:

                         GAME
                          │
              ┌───────────┴───────────┐
              │                       │
        SimulationSystem          SaveSystem
              │
      ┌───────┼────────┬──────────┐
      │       │        │          │
   Workers  Mining  Machines   Economy
      │       │        │          │
      └───────┼────────┴──────────┘
              │
        ResourceSystem
              │
       ┌──────┴──────┐
       │             │
    Physics       Inventory
       │
    Rendering
       │
       UI


There's an important distinction:

**Rendering should not own gameplay.**

A gem's visual representation shouldn't decide whether the gem exists, how much it is worth, or whether it belongs in the warehouse.

---

Game
→ coordinates the whole application

GameState
→ contains persistent/current game state

SimulationSystem
→ advances game time and tells systems to update

World
→ contains the physical game world

Systems
→ contain gameplay rules

Entities
→ represent things existing in the world

# 3. The most important systems

## Core

### `Game.cs`

The central coordinator.

It shouldn't contain gameplay logic.

Its job is basically:


Start game
    ↓
Initialize systems
    ↓
Load save
    ↓
Start simulation


It knows that the systems exist, but shouldn't know how mining works.

---

### `GameTime.cs`

Controls game time.

For example:


GameTime
├── delta time
├── simulation speed
├── paused
└── offline time


This becomes especially useful later for idle mechanics.

---

### `EventBus.cs`

This could become extremely useful.

Instead of:


Worker → Machine
Worker → Economy
Worker → UI
Worker → Statistics


we can do:


Worker
   ↓
EventBus
   ↓
┌────────────┬──────────────┬──────────────┐
Machine      Statistics     UI


For example:


ResourceCreated
ResourcePickedUp
ResourceDelivered
MachineFinished
GemProduced
GemSold
WorkerUnlocked
PrestigePerformed


This dramatically reduces dependencies between systems.

---

# 4. World system

The world contains the actual game environment.


World
├── Terrain
├── Mine
├── Ground
├── Machines
├── Warehouse
└── Workers


### `WorldGrid.cs`

This is particularly important because your mine is grid-based.

It knows:


Grid cell
├── empty
├── stone
├── dirt
├── ore
├── occupied
└── destroyed


The grid is **gameplay data**.

The visual tiles are just the representation of that data.

# 5. Mining system

The mining system controls:


Mine
 ↓
Find mining jobs
 ↓
Worker takes job
 ↓
Dynamite
 ↓
Explosion
 ↓
Terrain destroyed
 ↓
Resources generated


Importantly:

**Mining does not own resource physics.**

It simply says:

> "These 17 stones have been created at this position."

Then the resource/physics systems take over.

# 6. Resources

I'd separate the **logical resource** from its physical representation.

For example:

```text
Resource
├── type = Stone
├── amount = 1
├── quality
└── state
```

And separately:

```text
ResourcePhysicsBody
├── position
├── velocity
├── collision
└── visual
```

This distinction will be very valuable.

# 7. Physics system

This is where your new requirement becomes important.

You have:

```text
                 MACHINE
                    │
                    ▼
              ┌───────────┐
              │  GEMS     │
              │  STONES   │
              └───────────┘
                    │
                    ▼
              physics falls
                    │
             ┌──────┴──────┐
             │             │
          ground         resources
             │             │
             └──────┬──────┘
                    ▼
                 settle
```

I'd create a dedicated:

### `PhysicsWorld.cs`

Responsible for:

* gravity
* collision detection
* collision resolution
* ground collision
* resource/resource collision
* sleeping/resting objects
* physics updates

And:

### `ResourcePhysics.cs`

Responsible for translating a resource into a physical object.

For example:

```text
Stone created
    ↓
ResourceManager
    ↓
PhysicsWorld.CreateBody()
    ↓
Stone falls
    ↓
Collides with ground
    ↓
Collides with other stones
    ↓
Eventually rests
```

### Important optimization

We should **not necessarily use Godot's full rigid-body physics for every stone and gem**.

If the game eventually produces hundreds or thousands of pieces, Android performance could suffer badly.

We should probably design the architecture so that the physics implementation can later be optimized.

For example:

```text
IPhysicsBody
      │
      ├── GodotPhysicsBody
      │
      └── OptimizedResourcePhysicsBody
```

We don't have to implement that abstraction immediately, but designing around the possibility is smart.

---

# 8. Machines

Machines should have a very simple responsibility:

> **Transform inputs into outputs.**

For example:

```text
ProcessingMachine

Input:
Stone

Processing:
2 seconds

Output:
Gem
```

The machine doesn't decide where the gem goes.

It produces the gem.

Then:

```text
Machine
   ↓
GemCreated
   ↓
ResourceSystem
   ↓
PhysicsSystem
```

So the gem physically falls out of the machine.

That's a nice clean separation.

---

# 9. Logistics

This deserves its own system because logistics is one of the main gameplay mechanics.

```text
LogisticsSystem
│
├── Pickup jobs
├── Delivery jobs
├── Machine supply jobs
├── Warehouse jobs
└── Gem sorting jobs
```

Workers ask:

> "What job should I do?"

The job system responds:

```text
Available jobs:

Mining
Transport stone
Feed machine
Transport gems
Sort red gems
Transport gems to warehouse
```

The worker chooses a suitable job based on:

* assigned role
* distance
* priority
* carrying capacity
* availability
* current situation

---

# 10. Worker system

I'd keep workers relatively dumb.

Don't make:

```text
Worker.cs
```

contain:

* mining
* pathfinding
* inventory
* economy
* machine logic
* resource generation
* market logic

Instead:

```text
Worker
│
├── WorkerAI
├── WorkerInventory
├── WorkerMovement
└── WorkerJob
```

And globally:

```text
JobSystem
```

creates jobs.

So the relationship becomes:

```text
JobSystem
    │
    ▼
Available Job
    │
    ▼
WorkerAI
    │
    ▼
Worker accepts job
    │
    ▼
WorkerMovement
    │
    ▼
Worker performs action
```

This is a very important architectural decision.

---

# 11. Worker climbing

Since workers can climb essentially anywhere, I would **not start with traditional navigation meshes**.

Instead, we can eventually make movement based on the terrain/grid.

Something like:

```text
             worker
               ↓
        ┌───┬───┬───┐
        │   │   │   │
        ├───┼───┼───┤
        │   │   │   │
        ├───┼───┼───┤
        │   │ █ │   │
        └───┴───┴───┘
```

The worker can:

```text
walk
climb
drop
jump/fall
```

depending on the terrain.

This could be considerably simpler than conventional pathfinding.

# 12. Inventory and storage

We should distinguish:

### Worker inventory

Small temporary inventory.

```text
Worker
└── Inventory
    ├── stone × 3
    └── gems × 1
```

### Machine inventory

```text
Machine
├── input
└── output
```

### Warehouse

Large persistent inventory.

```text
Warehouse
├── stone
├── red gems
├── blue gems
├── green gems
├── ...
└── yellow gems
```

The actual inventory logic belongs in the resource/logistics side, not in the UI.

It cares about:

 ↓

Money

Six gem colors:

Red

# 14. Progression

Progression should be completely separate from the economy.


UpgradeSystem
│
├── Mining upgrades
├── Worker upgrades
├── Logistics upgrades
├── Machine upgrades
└── Warehouse upgrades


And:

PrestigeSystem
│
├── Calculate prestige reward
├── Reset temporary progression
├── Keep permanent upgrades
└── Start new run


That means prestige doesn't have to know anything about how a worker actually mines.

It simply resets the appropriate game state.

---

# 15. Simulation system

This is especially important for an idle game.

I'd have:


SimulationSystem


coordinate the passage of game time.

Conceptually:


Simulation tick
      │
      ├── Worker updates
      ├── Job updates
      ├── Machine updates
      ├── Market updates
      ├── Physics updates
      └── Statistics updates


But we should **not necessarily update everything every frame**.

For example:

Physics          → every physics tick
Worker movement  → every physics tick
Machines         → event/timer based
Market           → every few seconds
Statistics       → every few seconds
Idle calculations → larger intervals


This will matter enormously on Android.

# 17. What should NOT communicate directly

I'd establish some rules now.

### ❌ Worker → Economy

A worker shouldn't directly change the player's money.

### ❌ Machine → UI

A machine shouldn't directly manipulate UI labels.

### ❌ UI → Worker internals

UI should send a command:

> "Assign this worker to mining."

rather than modifying ten fields inside the worker.

### ❌ Mining → Physics internals

Mining should create physical resources, not manually control their velocity/collision.

### ❌ Market → Worker

The market shouldn't care how workers operate.

This keeps the systems independent.

# 19. One thing I'd change from the start

Because you're targeting Android and expect potentially many workers and resources, I'd divide the game into two layers:

### Simulation layer

Worker data
Resource data
Machine data
Inventory
Economy
Jobs
Terrain


### Presentation layer

Worker sprites
Gem sprites
Stone sprites
Machine animations
Particles
UI
Camera
Effects


That means, eventually, the game could have **100 workers logically simulated without requiring 100 extremely expensive Godot nodes doing complicated work every frame.**

And the same applies to stones and gems.

This is something I'd design into the architecture **before** we start coding.

    WorldGrid.cs

That gives us a **vertical foundation** rather than creating an enormous empty architecture.

---


For this game, let's deliberately enforce:

> **One system = one responsibility.**

And:

> **Data ownership should always be obvious.**

For every new feature we add, we should be able to ask:

**"Which system owns this?"**

If the answer is something like *"Well, `Game.cs` probably needs to do it..."*, that's a warning sign.

I think this gives us a very solid foundation for the next step: **define the actual data model and communication events**—things like `ResourceCreated`, `JobCreated`, `JobCompleted`, `MachineFinished`, `ResourcePickedUp`, `ResourceDelivered`, `GemSold`, etc. That should happen **before we define the individual worker/machine scripts**, because those events will form the backbone of the whole game.
