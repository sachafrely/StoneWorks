StoneWorks — Technical Architecture

Authority
--------
This document is authoritative for:
- system responsibilities
- ownership boundaries
- communication rules
- system interactions
- architectural decisions

GodotProjectStructure.txt is authoritative for physical file/folder organization.
When architecture changes, update both documents together.

Core rule
---------
Systems own gameplay rules and system-level data.
Entities represent things that exist in the world.
Scenes represent Godot composition and presentation/physical representation.
UI presents state and sends commands; it does not own gameplay rules.
Systems communicate through narrow APIs/commands and events rather than reaching into each other's internals.

Every C# script should have a short comment at the top describing its role, rules, and important dependencies.

UI observes state/events and sends commands to the appropriate system. Rendering never becomes the owner of gameplay state.


2. Core vs Simulation
---------------------

Core contains application-wide infrastructure and state that should exist independently of the simulation loop:

Game
- application coordinator
- creates/connects systems
- controls startup/shutdown
- does not contain gameplay rules

GameState
- current persistent gameplay state shared at save/load boundaries
- money, progression, unlocked content, relevant world state, etc.
- is a state container, not a system that performs gameplay

GameTime
- simulation clock
- pause/speed/time information
- offline-time calculation support

EventBus
- lightweight publish/subscribe mechanism for domain events
- events communicate facts, not commands
- should not become a hidden service locator

Simulation contains the rules for advancing the game:

SimulationSystem
- owns the simulation update loop and update scheduling
- decides which systems receive which simulation ticks
- coordinates ordering where ordering matters
- does not implement mining, worker AI, market rules, etc.

SimulationTick
- small value/context describing an update step when needed

StatisticsSystem
- observes simulation/domain events and periodically records statistics
- does not drive gameplay

Not everything updates every frame:
- physics: physics ticks
- worker movement/AI: simulation ticks as required
- machines: timers/events or appropriate simulation ticks
- market: coarse intervals
- statistics: coarse intervals
- idle/offline calculations: explicit larger intervals


3. World, Mine, and WorldGrid
-----------------------------

World is the top-level owner of the spatial game world.
It knows what world-level entities/areas exist and provides the spatial context in which systems operate.
It does not own mining rules, worker AI, economy rules, or resource physics.

Mine is the gameplay representation of the mine area.
It owns the mine's terrain/grid state and exposes operations such as querying a cell and destroying terrain.
MiningSystem decides when and why terrain is mined; Mine performs the world-state operation.

WorldGrid is the data structure used by the mine to represent grid cells.
It contains gameplay-relevant cell state, not TileMap visuals.
Typical cell states may include empty, stone, dirt, ore, occupied, and destroyed.

Terrain is the visual/scene representation of terrain data.
Changing a tile must not silently become the source of truth for mine state.

Relationship:

World
  └── Mine
       └── WorldGrid (gameplay data)
             ↓
          Terrain / TileMap (visual representation)

Machines, workers, warehouse, and other world entities exist in the World but remain owned by their appropriate systems/entities.


4. Resources: logical data vs physical representation
------------------------------------------------------

Do not create a mandatory central ResourceManager merely to make resources globally accessible.
For the current game design, it would become a god-object risk.

ResourceData
- static definition/configuration of a resource type
- name, category, base value, visual references, etc.

ResourceType
- stable identifier/category for resource types

Resource
- logical resource entity/state
- type, quantity, quality and relevant gameplay state
- has no responsibility for collision simulation

ResourceStack
- grouped logical inventory quantity where appropriate

ResourcePhysics / PhysicsBody
- physical representation and runtime physics state
- position, velocity, collision, sleeping/resting state, etc.

PhysicsWorld
- owns physical simulation and collision resolution

The logical resource and physical body must remain separable:

Resource created
    ↓
logical Resource
    ↓
physical representation created when required
    ↓
PhysicsWorld simulates it
    ↓
resource can later be picked up/stored
    ↓
physical representation can be removed while logical ownership continues

This allows the game to avoid unnecessary physics objects for resources that are already stored and leaves room for a future optimized resource-physics implementation.

A central ResourceManager may be introduced later only if a concrete ownership/lookup requirement appears. It is not part of the baseline architecture.


5. Physics
---------

PhysicsWorld owns:
- gravity
- physical update
- collision detection/resolution
- ground/environment collision
- resource/resource collision
- sleeping/resting behavior

ResourcePhysics translates logical resources that need physical simulation into physical bodies.

The first implementation may use Godot physics where appropriate. The architecture must not assume that every resource permanently requires a full rigid-body node; performance-oriented implementations can be introduced later behind the same responsibility boundary.

Mining and machines may request creation of physical resources, but they do not directly manipulate collision internals.


6. Mining
---------

MiningSystem owns mining rules:
- deciding available mining work
- validating mining actions
- applying mining effects
- creating resources as a consequence of mining

MiningJob is a job type describing a mining task.
Dynamite is a mining action/tool rather than a general physics system.

MiningSystem requests Mine operations. It does not edit TileMap nodes directly and does not resolve resource collisions.

Basic flow:

Worker receives MiningJob
      ↓
MiningSystem validates/performs mining
      ↓
Mine changes WorldGrid
      ↓
Resources are created
      ↓
Resource/Physics systems handle resulting physical resources
      ↓
Events inform statistics/UI/etc.


7. Jobs vs Logistics
--------------------

JobSystem owns the generic job lifecycle:
- available jobs
- claiming/assignment
- job state
- priorities/eligibility
- completion/cancellation

It should know how a job behaves as a job, not how every gameplay domain performs the work.

Domain systems create domain-specific jobs:
- MiningSystem creates MiningJob
- LogisticsSystem creates transport/delivery jobs
- Machines may request supply work through LogisticsSystem

LogisticsSystem owns logistics rules:
- deciding what should be transported
- pickup/delivery requirements
- storage routing
- machine supply and warehouse movement
- creating the appropriate transport jobs

Therefore:

LogisticsSystem
    ↓ creates logistics work
JobSystem
    ↓ assigns/manages job lifecycle
WorkerAI
    ↓ executes accepted job
WorkerMovement / WorkerInventory
    ↓ performs physical actions

JobSystem is the generic job mechanism. LogisticsSystem is a domain system that uses it. They are not duplicates.


8. Workers
----------

Worker is the world entity/state for an individual worker.

WorkerAI
- chooses/accepts work and decides the worker's next action
- does not contain mining/economy/machine rules

WorkerMovement
- movement, climbing, falling and navigation execution
- should use mine/world data rather than requiring a traditional navigation mesh initially

WorkerInventory
- temporary carried logical resources

WorkerJob
- current job reference/state from the worker's perspective

WorkerManager should only exist if a concrete collection/lifecycle ownership need appears. Do not create manager classes merely because they are common in other projects.

Workers should request/perform actions through system APIs rather than directly modifying unrelated systems.


9. Machines
-----------

Machine represents a machine entity and its local state.
MachineManager is only justified if centralized machine lifecycle/lookup is required.

ProcessingMachine owns machine-specific processing state/rules.
MachineRecipe defines configurable input/output/timing data.

A machine transforms inputs into outputs. It does not decide warehouse routing, economy effects, or UI presentation.

Example:

Machine processing completes
      ↓
logical Gem created
      ↓
physical Gem created if it should enter the world physically
      ↓
PhysicsWorld handles falling/collision
      ↓
Logistics later handles pickup/storage


10. Economy
-----------

EconomySystem owns economy-wide rules.
Market owns market state/price behavior.
GemMarket contains gem-specific market configuration/rules only if that separation remains useful.
SellingSystem performs selling transactions through the economy APIs.

Economy must not depend on worker implementation details.
Selling changes game state through the economy system, which can publish an event for statistics/UI.


11. Progression
---------------

UpgradeSystem owns upgrade effects and purchase rules.
UnlockSystem owns content-unlock rules.
PrestigeSystem owns prestige calculation/reset rules.

Progression may read economy/game state through defined interfaces, but progression systems should not reach into unrelated entity internals.


12. Save system
---------------

SaveSystem owns serialization/deserialization and save/load operations.
SaveData is a persistence DTO/container, not the runtime owner of gameplay rules.

Systems expose the state required for saving through explicit save interfaces or state objects.
SaveSystem should not manipulate gameplay internals directly.


13. Godot scenes and C# systems
-------------------------------

Scenes are composition and presentation boundaries, not the architecture's gameplay authority.

Main scene
  ↓
Game node / application coordinator
  ↓
creates or connects runtime systems
  ↓
systems operate on gameplay state
  ↓
scene nodes present/represent the relevant state

Rules:
- A scene script may call a system's public command/query API.
- A scene script must not modify another system's private state.
- UI should send commands and subscribe to relevant events/state changes.
- Visual nodes may represent entities, but the visual node is not automatically the source of truth.
- Systems should not search the scene tree for arbitrary nodes to perform gameplay.
- Avoid global singletons unless a service genuinely must be globally accessible and has a clear lifecycle.

For physical entities such as workers, machines and physical resources, the Godot node can be the visual/physics representation while logical gameplay state remains owned by the appropriate entity/system.


14. Communication rules
-----------------------

Prefer this:

UI → command/API → owning system
System → domain event → EventBus → interested systems/UI

Avoid this:

UI → private worker fields
Machine → UI labels
Worker → Economy internals
Mining → Physics internals
Market → Worker internals
System → arbitrary GetNode() calls across the scene tree

Commands mean "please perform this action".
Events mean "this fact happened".
Queries mean "give me read-only information".

Use direct calls when a clear ownership relationship exists. Do not use EventBus for every method call.

Examples of useful events:
- ResourceCreated
- ResourcePickedUp
- ResourceDelivered
- MachineFinished
- GemProduced
- GemSold
- WorkerUnlocked
- PrestigePerformed


15. System size and manager policy
----------------------------------

Start smaller than the final design.
A planned system/file is not automatically required.

Create a separate system when at least one of these is true:
- it owns a meaningful set of rules
- it has a distinct update cadence/lifecycle
- it has an independent reason to change
- keeping it in another class would create a clear responsibility violation

Avoid:
- empty manager classes
- one-class wrappers with no ownership value
- global registries without a concrete need
- giant systems containing several unrelated domains

It is acceptable for an early implementation to have fewer classes than the planned architecture. Split classes when real complexity appears, not in anticipation of it.

17. Architectural decision summary
-----------------------------------

1. Core = application infrastructure/state; Simulation = advancing gameplay.
2. No baseline ResourceManager; resources are owned through their actual domain/state holders.
3. World owns the world; Mine owns mine terrain state; WorldGrid stores grid data; Terrain renders it.
4. Logical Resource and physical ResourcePhysicsBody are separate responsibilities.
5. JobSystem manages generic jobs; LogisticsSystem owns transport/logistics rules and creates logistics jobs.
6. Godot scenes represent/combine things; C# systems own gameplay rules; communication uses APIs, queries and events.
7. Managers are optional and must earn their existence through a real ownership/lifecycle need.
8. Start with the smallest useful implementation and split systems only when complexity justifies it.
