StoneWorks — Godot Project Structure

Purpose
-------
This document defines where project files belong in the Godot project and how planned C# scripts map to Godot scene nodes.

TechnicalArchitecture.txt is authoritative for system responsibilities, ownership, communication, and interactions. This document is authoritative for physical Godot folder organization, scene structure, node types, and script-to-node attachment.

The repository contains the planned C# script skeletons. Skeletons define class/file boundaries only; they do not mean the gameplay functionality is implemented.

2. Folder responsibilities
---------------------------

Scenes/
    Godot scene composition. Scenes represent visual/physical entities and their node structure. Core gameplay rules belong in systems, not scenes.

Scripts/
    C# gameplay code, systems, entities, controllers, presentation infrastructure, and shared infrastructure. Scripts are grouped by responsibility/domain.

Managers/
    The three intentional centralized lifecycle/ownership managers: ResourceManager, WorkerManager, and MachineManager.

Assets/
    Visual assets such as sprites, tilesets, background layers, machine art, worker art, resource art, and UI art.

Data/
    Static/configurable game definitions such as resources, machines, upgrades, and markets.

Audio/
    Music and sound effects.

Saves/
    Save-related runtime data or save-file support. Do not put gameplay rules here.

Docs/
    Project documentation.

The three managers intentionally live in Scripts/Managers. Older comment-only Manager.cs placeholders inside Resources, Workers and Machines are deprecated references and are not part of the active architecture.

GameResource.cs is the logical resource entity. It is deliberately named after its C# class to keep the file/class relationship clear and avoid confusion with Godot.Resource.

ParallaxBackgroundController coordinates scripted parallax presentation and the active camera. ParallaxLayerController controls one visual layer's depth factor and optional wrapping. These scripts are presentation infrastructure, not gameplay systems.

JobSystem belongs to Logistics because it is the generic job mechanism used by domain systems such as Mining and Logistics.


4. Godot node types and script attachments
-------------------------------------------

This section defines which C# scripts are attached to Godot nodes and which scripts remain plain runtime/data classes.

Important rule:
- A script is attached to a Godot node only when the script represents a persistent scene object, runtime system, controller, or presentation object that benefits from Godot's scene tree and lifecycle.
- A script does NOT need its own node merely because it is a C# class.
- Data/value objects such as ResourceType, ResourceData, ResourceStack, MachineRecipe, SaveData, and job/data classes remain plain C# objects unless implementation later gives them a concrete Godot resource/node role.
- Node types below describe the intended architecture. They do not imply that every planned scene has already been created.

4.1 Main scene and application root

Scenes/main.tscn
    Main — Node2D
        Script: Game.cs
        Role: Top-level application coordinator.

        Child nodes planned:
        ├── Managers — Node
        │   ├── ResourceManager — Node
        │   │   Script: ResourceManager.cs
        │   ├── WorkerManager — Node
        │   │   Script: WorkerManager.cs
        │   └── MachineManager — Node
        │       Script: MachineManager.cs
        │
        ├── Simulation — Node
        │   └── SimulationSystem — Node
        │       Script: SimulationSystem.cs
        │
        ├── World — Node2D
        │   Script: World.cs
        │
        └── UI — Control
            Script: MainUI.cs

The exact child-node names may change during scene construction, but the script ownership must remain consistent with this document.

The current main.tscn contains a Main Node2D. The Game.cs script is intended for this node.


4.2 Core scripts

Game.cs
    Node2D — Main
    Attached: Yes
    This is the root application coordinator.

GameState.cs
    No node attachment.
    Plain runtime state object owned/used by Game and Core systems.

GameTime.cs
    No node attachment.
    Plain runtime time/state service. It does not need an independent scene node.

EventBus.cs
    Node — EventBus runtime service, normally created as a child of Main/Game.
    Attached: Yes, when the event bus is instantiated as a scene-tree service.


4.3 Managers

ResourceManager.cs
    Node — ResourceManager
    Attached: Yes
    Central owner of logical resource lifecycle and transfers.

WorkerManager.cs
    Node — WorkerManager
    Attached: Yes
    Central owner of the worker roster and worker lifecycle.

MachineManager.cs
    Node — MachineManager
    Attached: Yes
    Central owner of machine registration and lifecycle.

Only these three scripts are centralized managers. Other systems must not be turned into additional global managers merely for convenience.


4.4 World and environment

World.cs
    Node2D — World
    Attached: Yes
    Top-level owner of the spatial gameplay world.

WorldGrid.cs
    Node — WorldGrid
    Attached: Yes
    Child/service node of World or Mine containing authoritative grid state.

Terrain.cs
    TileMapLayer (or the project-equivalent TileMap node if required by the chosen Godot version)
    Attached: Yes
    Owns terrain/tile presentation and terrain-facing scene representation. It does not own mining rules.

Mine.cs
    Node2D — Mine
    Attached: Yes
    Represents a mine area within World.

ParallaxBackgroundController.cs
    Node2D — ParallaxBackgroundController
    Attached: Yes
    Presentation controller for the scripted parallax background and active camera.

ParallaxLayerController.cs
    Node2D — ParallaxLayerController
    Attached: Yes
    One child node per parallax layer. Controls that layer's depth factor and optional wrapping.

Camera2D
    Godot built-in node; no custom script required by the current architecture.
    ParallaxBackgroundController references the active camera rather than replacing camera responsibilities.


4.5 Workers

Worker.cs
    CharacterBody2D — Worker
    Attached: Yes
    Physical/visual worker entity.

WorkerAI.cs
    No separate node by default.
    Runtime worker decision-making component used by Worker and WorkerManager.

WorkerJob.cs
    No node attachment.
    Job/data object describing work assigned to a worker.

WorkerMovement.cs
    No separate node by default.
    Worker movement component operating on Worker's CharacterBody2D.

WorkerInventory.cs
    No separate node by default.
    Worker inventory state/service owned by the worker domain.

If WorkerMovement or WorkerAI later requires independent Godot lifecycle processing, it may become a child Node, but this is not the default architecture.


4.6 Resources and physical resource objects

GameResource.cs
    Node2D — resource scene root when a physical resource is represented in the world.
    Attached: Yes for physical resource scenes.
    Represents the logical identity/state of one resource while allowing a scene representation.

ResourceData.cs
    No node attachment.
    Static/configurable resource definition.

ResourceType.cs
    No node attachment.
    Enum/type definition.

ResourceStack.cs
    No node attachment.
    Lightweight logical quantity/type container.

Stone.tscn / Gem.tscn
    Root: Node2D with GameResource.cs.
    Add physics child nodes when required by implementation.

Logical resources that are not currently represented physically in the world must not create unnecessary nodes.


4.7 Physics

    No separate node by default.
    Shared physics-state/helper abstraction. Actual physical scene bodies use Godot physics nodes such as CharacterBody2D, RigidBody2D, StaticBody2D, or Area2D as appropriate.

6. Node attachment rules
------------------------

- Every script that inherits from Node/Node2D/Control/CharacterBody2D/etc. is expected to have a corresponding Godot node when that runtime role is active.
- A script that does not inherit from a Godot Node should normally not be attached to a scene node.
- Do not create empty nodes solely to attach helper/data classes.
- Prefer one meaningful script per scene root when a script represents that object's primary behavior.
- Child components such as WorkerAI, WorkerMovement, and WorkerInventory remain plain C# components unless they genuinely require independent Godot lifecycle processing.
- Runtime systems may be grouped under non-scripted Node containers for scene organization.
- The three managers are the only centralized manager scripts.
- Scene composition belongs to Godot scenes; gameplay ownership remains in the C# architecture.


7. Naming and organization rules
--------------------------------

- Use PascalCase for C# script and scene names, except the existing project entry scene main.tscn.
- Keep scripts grouped by the system/domain they primarily belong to.
- Keep the three centralized managers in Scripts/Managers.
- Keep logical resource data separate from physical resource simulation.
- Keep gameplay data separate from visual assets.
- Keep UI presentation separate from gameplay rules.
- Keep background artwork in Assets/Backgrounds/.
- Keep scripted parallax controllers in Scripts/World/.
- Avoid creating folders only for theoretical future files when an existing folder already represents the correct domain.
- When a new system is introduced, update this document and TechnicalArchitecture.txt together.
- Do not move a script merely to match a planned list; classify it by its actual responsibility.
- Prefer the smallest useful number of scripts; split responsibilities when real complexity appears.
