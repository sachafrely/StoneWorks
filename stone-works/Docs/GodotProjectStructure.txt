StoneWorks — Godot Project Structure

Purpose
-------
This document defines where project files belong in the Godot project.

TechnicalArchitecture.txt is authoritative for system responsibilities, ownership, communication, and interactions. This document is authoritative for physical Godot folder organization and planned file locations.

This is a planned structure. Empty folders and planned scripts do not mean the corresponding functionality has been implemented.

2. Folder responsibilities
---------------------------

Scenes/
    Godot scene composition. Scenes represent visual/physical entities and their node structure. Core gameplay rules belong in systems, not scenes.

Scripts/
    C# gameplay code, systems, entities, controllers, and shared infrastructure. Scripts are grouped by responsibility/domain.

Assets/
    Visual assets such as sprites, tilesets, background layers, machine art, worker art, resource art, and UI art.

Data/
    Static/configurable game definitions such as resources, machines, upgrades, and markets.

Audio/
    Music and sound effects.

Saves/
    Save-related runtime data or save-file support. Do not put gameplay rules here.

Docs/
    Project documentation. TechnicalArchitecture.txt defines architecture; this document defines physical organization.

No dedicated ParallaxBackground.cs is planned initially. The parallax background is presentation/scene composition and should use Godot's parallax/camera functionality rather than introducing gameplay code for it. A dedicated script should only be added later if the background develops real runtime behavior that cannot be handled by scene configuration.

Only create a planned script when its functionality is actually needed. The planned list is an architectural map, not a requirement to create every file immediately.

There is intentionally no ResourceManager, WorkerManager, or MachineManager in the baseline map. A manager may be added later if a concrete lifecycle, ownership, or lookup requirement justifies it.

JobSystem belongs to Logistics because it is the generic job mechanism used by domain systems such as Mining and Logistics. TechnicalArchitecture.txt defines the responsibility boundary.

The exact number, artwork and movement strength of the background layers are still to be decided.


5. Naming and organization rules
---------------------------------

- Use PascalCase for C# script and scene names, except the existing project entry scene main.tscn.
- Keep scripts grouped by the system/domain they primarily belong to.
- Keep logical resource data separate from physical resource simulation.
- Keep gameplay data separate from visual assets.
- Keep UI presentation separate from gameplay rules.
- Keep background artwork in Assets/Backgrounds/.
- Keep parallax scene composition in the relevant Godot scene rather than creating a script without a concrete runtime responsibility.
- Avoid creating folders only for theoretical future files when an existing folder already represents the correct domain.
- When a new system is introduced, update this document and TechnicalArchitecture.txt together.
- Do not move a script merely to match a planned list; classify it by its actual responsibility.
- Prefer the smallest useful number of scripts; split responsibilities when real complexity appears.


6. Architecture boundary
-------------------------

This document deliberately does not repeat the detailed architecture rules and communication flows from TechnicalArchitecture.txt.

Use TechnicalArchitecture.txt for questions such as:
- Which system owns a piece of data or gameplay logic?
- Which systems may communicate directly?
- When should events/interfaces be used?
- What responsibilities belong to an entity versus a system?
- How do Godot scenes communicate with runtime systems?

Use this document for questions such as:
- Which Godot folder should contain this file?
- Where should a new C# system be placed?
- Where should a scene, asset, or data definition live?
- Where should parallax background artwork and scene composition live?

The two documents should remain synchronized when the architecture or physical organization changes.
